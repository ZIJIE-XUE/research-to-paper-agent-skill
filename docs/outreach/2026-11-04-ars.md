# 分享一个面向机器学习实证的实验—主张交接 skill，想请教复审与来源记录设计

我维护了一个独立的 [ML Research & Paper](https://github.com/ZIJIE-XUE/research-to-paper-agent-skill)，想在这里分享其中的实验与论文证据交接设计，请研究工作流使用者帮忙挑问题。

阅读 ARS 的介绍和架构后，我借鉴了按模式进入、证据交接、审稿前/交付前检查及逐条意见复审的思路，并在仓库设计说明中注明来源。实现是独立编写的，不是 ARS 官方分支，也不声称兼容 ARS Material Passport 的完整 schema 或运行时。

当前尝试解决的具体问题是：一项本地 ML 实验跑完之后，下一次会话怎么核对它的结果，以及论文中的断言是否确实回到了那份材料。

- 运行前冻结协议、代码与列明的输入，按队列、超时和总预算执行，保留失败。
- 复用成功任务时重新检查输出哈希；输入或方案变化后使用新的实验 ID。
- 在主张台账中记录原文/表格定位或运行回执；引用关系区分存在、元数据、定位及支持判断。
- 将审稿前与最终报告绑定到具体文件版本；复审按原问题和验收标准核查，避免仅凭作者回应关闭问题。

有一个无需 API Key、无需额外包的离线工具示例：

```bash
git clone https://github.com/ZIJIE-XUE/research-to-paper-agent-skill.git
cd research-to-paper-agent-skill
python examples/quick_demo.py
```

它只生成合成分类数据，执行4个任务并检查复用与来源，不是完整研究或真实市场/临床数据证据。Windows 与 Ubuntu 的公开 CI 运行28项测试和该示例。项目采用 MIT 许可，入口文档有中英文。

我比较想请教：

1. 从实验结果交给写作/复审时，目前这些字段还遗漏了哪些关键证据？
2. 哪些情况容易“文件都对得上，但科学解释已经过度”？应怎样把这些情况更清楚地暴露给作者？
3. 对已有实验结果的论文，什么样的最小交接示例最有助于研究者实际试用？

脚本只检查登记关系、运行来源与文件版本；文献语义、数据真实性、主张提取是否完整仍需要实际核查。内部 AI 审查也不等同于真人外审。欢迎用可公开或合成的小案例反馈，避免上传私人论文或受限数据。
